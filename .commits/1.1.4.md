## Rules (Required)

From [AGENTS.md](../AGENTS.md#internal-version-proposed). The internal version scheme is marked Proposed there; the user may re-seed or change it.

- Format `<breaking>.<major>.<minor>.<build>`, seeded unbuilt at `1.1.4.0`. Fields are ASCII digits only, without zero padding. A reader of the version file strips its line end before it parses.
- Major and minor each range 0 to 9. The build field ranges 0 to 99 (user, 17 November 2026). It counts up, `1.1.4.9 -> 1.1.4.10`, and carries at 99: `1.1.4.99 -> 1.1.5.0`, `1.1.9.99 -> 1.2.0.0`, `1.9.9.99 -> 2.0.0.0`. A build field of 100 is refused. The earlier one-digit build field was superseded; no build was accepted under it.
- A build is qualifying when the consumer's acceptance builds this fork commit from its archive and passes its required checks. Per-PR focused evidence (incremental build, focused checks and council review) qualifies a merged PR for its own build number and focused build record; full acceptance stays at the family or batch run. The first qualifying build advances the version to `1.1.4.1`.
- A merged PR that changes source, tests, build files, tools or dependencies gets its own build number. A tools-only change rides on the next qualifying build. Failed, configure-only and documentation-only work does not advance the version.
- Notes are Markdown, grouped by three-part family in `.commits/<breaking>.<major>.<minor>.md`. Every build-number transition is recorded here with before and after versions, source identity, profile, checks and remaining limits.
- A later upstream release gets a new `native/planegcs-<release>` branch; changes are re-applied and re-qualified there. A version number never implies compatibility. A commit that a consumer has pinned is never rewritten or force-pushed.
